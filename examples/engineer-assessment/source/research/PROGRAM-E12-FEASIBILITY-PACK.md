## Five instruction conditions

Hold source bytes, model/runtime, fresh-context rule, number of proposals, a minimal raw-output envelope, calls, time/token ceiling and available tools fixed. Use one topic × one condition per fresh attempt. Randomize execution and blind presentation order with separate recorded seeds. Every arm returns raw proposal text; the capture system assigns stable proposal IDs **after** receiving the raw output. Do not require the ordinary or generic arms to fill mechanism, prediction, defeat, prior or rival fields. After raw output is sealed, a separate arm-blind extraction pass codes those common analysis fields from each proposal, leaving absent evidence blank and retaining exact source spans. A and B also preserve their treatment-specific intermediate output for method-fidelity coding. This tests whether the method *causes* those operations to appear instead of giving them to every arm through the form.

| Arm | Extra authoring instruction |
| --- | --- |
| O ordinary | “Propose research questions or tests that could help decide what to do about this observation.” |
| G generic novelty benchmark | “Find unusual but useful research questions or tests that ordinary analysis might miss.” |
| A failure map | “First map observation → possible causes → consequence, then propose tests. Preserve more than one plausible cause.” |
| B prior/rival contrast | “For each proposal, identify the closest known prior and a rival explanation with a prediction that differs under one observation.” |
| A+B composition | Apply both A and B in that order; retain their intermediate outputs and exact candidate IDs. |

The completed AI feasibility cut used **five arms**. The primary E12 factorial still uses O/A/B/A+B; G is an extra generic-novelty benchmark. The [unrun v1 allocation](program-novelty/e12-feasibility/assignments.json) required common semantic fields and could partly teach the controls; it is retained as a design failure. The [unrun v2 successor](program-novelty/e12-feasibility/assignments-v2.json) preceded the corrected excerpts and exact prompt. The v4 cut passed two AI control-leakage audits, but its raw review text revealed all five arms in a later inference audit. Before any scored confirmatory run, independent stewards and reviewers must resolve that masking failure and the unequal authoring cost.

## What a feasibility attempt records

For each assigned cell, save the literal source pack, instruction, model and tool versions, prompt hash, shuffle seed, input/output tokens where available, elapsed time, raw first output, each raw idea ID, no-output/error/truncation, and any later normalization. A blind coder checks **method fidelity**: whether A really maps causes, B really finds a closest prior and opposing prediction, and G actually proposes an unusual usable distinction. A source-backed no-opening is valid method use when the case truly affords none; a missing output is an execution failure. Then a separate blind reviewer checks same-prediction duplicates against the **raw** O/G/A/B outputs and evaluator-only archive, followed by feasibility and usefulness judgment. Keep first ratings and disagreement before adjudication.

The completed preflight used three topics × five arms × one fresh attempt = **15 generation cells**, producing two proposals per cell. It then ran two AI first reviews per **proposal**, yielding **60 ratings**; the earlier estimate of 30 per-cell reviews was superseded before review execution. These counts support format/cost diagnosis, not a powered novelty-yield estimate or extrapolation across research topics. Actual model calls and token/wall costs are in the receipts; compute was not matched. No participant data were used.

The [v2 frozen 15-cell allocation](program-novelty/e12-feasibility/assignments-v2.json) records source hashes, the raw proposal envelope, post-generation extraction fields, exact arm instructions and randomized execution order (`AB` is the A+B arm). `python3 tools/build_e12_feasibility_assignments.py check --version v2` replays it without a model call; `--version v1` still checks the retained predecessor. Both are **prepared-unrun**. Because v2 does not pin the corrected excerpts, new prior cards or exact prompt, it was not a ready generation allocation. The [v3 candidate allocation](program-novelty/e12-feasibility/assignments-v3.json) pinned its packet bytes and spelled out AB, but remained unrun as a five-arm comparison because the first B probe found weak closest-prior evidence. ## Go/no-go for a later E12 comparison

Proceed to a separately frozen E12 batch only if: source facts are neutral and identical across arms; the raw envelope does not teach the treated operations; blind extraction preserves real missingness and does not add mechanisms; first reviewers can identify source-supported versus speculative premises and have bounded disagreement; arm labels are not obvious from normalized formatting; raw-to-selected lineage survives; and every attempt has an outcome and cost receipt. If a gate fails, repair the packet and retain the failed feasibility result. A successful preflight establishes **operational readiness only**. The later study still needs independent source topics, a precision plan, matched cost, execution allocation and untouched confirmation topics before any useful-workflow claim.
